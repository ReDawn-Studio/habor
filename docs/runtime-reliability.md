# Agent 安装与运行可靠性

## 已确认的问题

本次 `ACP connection closed` 发生在模型请求之前。DSH 启动函数会为安装包的依赖生成
`~/.dsh/profiles/node_modules` 链接，其中 `send` 已存在为普通空目录，官方链接维护函数因此抛错并退出。
现场证据能确定目录类型冲突，不能确定哪个程序创建了这个空目录。

这不是 Windows 独有的系统故障：同一个“普通目录占用依赖链接位置”的条件也会使其他平台失败。
Windows 的 `.cmd` 启动、路径与进程回收差异是另外需要适配的问题。

原先 habor 的集成存在三处缺口：

1. `--version` 成功只说明入口能运行，不能说明 Agent 的插件树和协议服务能启动。
2. 程序版本虽按目录隔离，生成配置与依赖链接却写到原生 DSH 的共享目录；多个版本、进程和原生客户端会争用这些文件。
3. ACP 子进程的 stderr 被丢弃，用户只得到连接关闭这一结果，无法看到启动失败原因。

## 实现的约束

| 层面 | 处理方式 |
| --- | --- |
| 安装事务 | 暂存下载 → 包标识 → 版本 → 可用的离线协议检查 → 原子启用。任何检查失败都保留旧版本。 |
| 检查范围 | DSH、Codex、Kimi 启动真实进程并执行 `initialize`；其他客户端仍是版本检查。`active.json.checks` 记录实际执行范围。 |
| DSH 运行配置 | 每个进程创建独立临时 profile；直接以选定安装包的文件 URL 为插件解析锚点，不创建共享依赖链接。 |
| 原生用户数据 | `DSH_HOME` 的设置、凭据和会话仍由原生插件读取；habor 不复制密钥、不修复或覆盖原生 profile。 |
| 故障边界 | ACP 启动及会话建立超时为 30 秒；失败释放进程，下一次操作可以重新连接。 |
| 诊断 | 记录有上限、脱敏的 stderr，显示退出码或超时原因；不会把子进程原始输出直接绘制到终端。 |
| 退出 | 正常关闭先结束 stdio，让运行时释放资源；超时再回收所属进程树。强制终止遗留的临时目录不会被复用。 |

离线检查不发送 prompt，不验证模型额度或 API Key，也不应显示“账号已认证”。
DSH 的桥接仍与已验证的官方运行时版本绑定；升级版本需要重新执行真实运行时测试。

## 验证方式

```sh
pnpm test
pnpm test:dsh-local
pnpm test:dsh-isolation
node packages/cli/test/native-provider-http.mjs --all --agent=dsh
```

DSH 集成测试需要先安装兼容的 DSH 客户端。测试使用临时目录、测试凭据与本地模拟 API。
`dsh-local-diagnostics.mjs` 故意放入冲突的 `send` 普通目录和损坏的原生 profile，验证对话、
原生凭据读取及失败后恢复，同时断言这些文件完全保留。
`dsh-runtime-isolation.mjs` 同时启动两个真实运行时，验证配置目录相互独立及正常关闭后的清理。
安装测试覆盖“版本检查通过，但协议启动失败”时旧版本继续生效。

`.github/workflows/runtime-regression.yml` 配置 Windows、Linux、macOS 的构建与上述 DSH 回归检查。
只有推送到远端并运行工作流后，才能得出对应 CI 平台的验证结论；本地测试不能替代这个结果。

新增客户端时，应定义它的非推理健康检查和需要隔离的生成文件，再加入安装事务，
不能默认所有厂商的认证、缓存目录或协议参数相同。
